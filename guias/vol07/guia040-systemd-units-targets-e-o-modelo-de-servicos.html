systemd: Units
e Targets

Em vez de um script que faz, um arquivo que descreve — e o PID 1 supervisiona.
040Guias Linux
Anatomia de um arquivo .service
[Unit] Description=Coletor After=network.target Wants=network.target Quem sou e de quem dependo. Vale para todo tipo de unit.
[Service] Type=simple ExecStart=/usr/bin/coletor User=coletor Restart=on-failure RestartSec=5s Como executar e supervisionar. Só existe em .service.
[Install] WantedBy=multi-user.target Lida só no enable: diz onde criar o link que faz o serviço subir no boot. Sem ela: No installation config specified.
Tudo é unit: .service processo .target marco .socket ativa sob conexão .timer agenda .mount montagem .path vigia caminho .device udev .slice cgroup
Requisito × ordem — dois eixos independentes

"B precisa de A?" — requisito

  • Wants= puxa A; se A falhar, B sobe assim mesmo. O padrão sensato.
  • Requires= puxa A; se A falhar ao iniciar, B é desativado.
  • BindsTo= se A parar a qualquer momento, B para junto.
  • Conflicts= iniciar B para A.

"B começa depois de A?" — ordem

  • After= / Before= — e nada mais.
  • Sozinho, Requires= não ordena: os dois sobem em paralelo.
  • Erro clássico: funciona na máquina lenta, quebra na rápida.
  • Quase sempre se quer o par: Requires=db.service + After=db.service.

Na prática
kali@kali: ~
$ systemctl cat ssh.service      # o arquivo + todos os drop-ins
$ systemctl show ssh -p Type -p Restart   # config efetiva, com os padroes
$ systemd-delta                  # o que neste sistema foge do padrao
$ sudo systemctl edit ssh.service         # cria o drop-in no lugar certo
$ sudo systemctl daemon-reload   # OBRIGATORIO apos editar unit na mao
$ sudo systemctl start tunel@servidor1    # template: %i = servidor1
⚡ Resumo rápido
  • Type= diz como o systemd sabe que subiu: simple (primeiro plano), forking + PIDFile= (daemon clássico), oneshot (roda e acaba).
  • Sem daemon-reload, a edição "não faz efeito" — o systemd opera com a versão em memória.
  • start repeated too quickly é sintoma, não causa: o serviço falha na partida por outro motivo.
  • Units de usuário em ~/.config/systemd/user/ dispensam sudo — substituem o @reboot do crontab.
🐉 No Kali
Serviços de rede vêm instalados e desabilitados de propósito — máquina de teste vive em rede hostil. Habilitar é ato consciente: systemctl enable --now ssh. O par Requires=+After=postgresql.service é o caso do Metasploit. E Type=forking sem PIDFile= é o erro nº 1 ao empacotar ferramenta: se ela tiver --no-daemon, use-a com Type=simple.
