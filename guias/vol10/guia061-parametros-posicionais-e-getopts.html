Posicionais
e getopts

A análise do script de coleta cresceu um if por vez: if [ "$1" = "-v" ]; then … shift; fi, três vezes. Funcionava — enquanto as opções viessem na ordem dos if, uma por vez, e nunca depois do arquivo. A análise de argumentos é a fronteira entre o que o usuário digitou e o que o script executa, e ela precisa de estrutura.
061Guias Linux
Cinco invocações razoáveis — e nenhuma mensagem de erro
coletar -n -v dados

O -v é testado primeiro: não é reconhecido, e VERBOSE fica 0.

coletar -vn dados

Agrupadas: "-vn" não é igual a "-v". Nada é reconhecido.

coletar dados -v

Opção depois do operando: simplesmente ignorada.

coletar -o dados

SAIDA vira dados e o arquivo fica vazio — argumento faltando.

coletar -- -rf

O -- vira nome de arquivo, e o -rf chega ao comando interno como opção.

1ªopcao=v · OPTARG vazio · OPTIND=1ainda dentro do -vn: o getopts desagrupa sozinho.
2ªopcao=n · OPTARG vazio · OPTIND=2terminou o -vn; agora aponta para $2.
3ªopcao=o · OPTARG=saida.txt · OPTIND=4consumiu dois argumentos. Aceita colado também: -osaida.txt.
4ªdevolve código ≠ 0 · OPTIND=4$4 não começa com hífen: acabaram as opções, o laço termina.
shift $(( OPTIND - 1 ))

Descarta os três argumentos já analisados: agora "$@" contém só os operandos e $# vale 2. Sem essa linha, o laço seguinte processaria -vn, -o e saida.txt como alvos — o erro nº 1 com getopts, e ele não emite aviso nenhum: só um alvo chamado -vn.

o esqueleto que resolve os cinco casos
while getopts ':vno:h' opcao; do   # : inicial = modo silencioso
  case "$opcao" in                 # o : DEPOIS da letra = exige argumento
    v)  VERBOSE=1 ;;
    n)  SIMULAR=1 ;;
    o)  SAIDA="$OPTARG" ;;
    h)  uso; exit 0 ;;             # --help e uso bem-sucedido: stdout, codigo 0
    :)  erro "-$OPTARG exige um argumento"; exit 2 ;;
    \?) erro "opcao invalida: -$OPTARG"; uso >&2; exit 2 ;;
  esac
done
shift $(( OPTIND - 1 ))            # a linha que todo mundo esquece
(( $# )) || { uso >&2; exit 2; }   # erro de uso: stderr, codigo 2

# opcoes LONGAS: getopts nao faz. O laco com case faz -- e trata o --
while (( $# )); do case "$1" in
  -v|--verbose) VERBOSE=1; shift ;;
  -o|--saida)   SAIDA="$2"; shift 2 ;;
  --saida=*)    SAIDA="${1#*=}"; shift ;;
  --)           shift; break ;;    # fim das opcoes
  -*)           erro "opcao desconhecida: $1"; exit 2 ;;
  *)            break ;;           # primeiro operando
esac; done

O if encadeado não tem caso de uso: custa o mesmo trabalho e falha em tudo. Curtas apenas → getopts; qualquer opção longa → laço com case. O getopt externo do util-linux faz as duas coisas, mas exige o idioma eval set -- "$OPCOES" e não existe no BSD/macOS.
Posicionais são um array: "$@" repassa, "$*" só exibe, e ${10} exige as chaves — $10 é lido como $1 seguido de 0. set -- a b c reescreve a lista (o -- inicial protege argumento com hífen). E shift falha com código 1 se pedir mais do que existe, sem alterar nada: teste $# antes, ou o laço nunca termina.
Todo caminho vindo de variável entra no comando depois de um --. Se $arquivo valer -rf ou --no-preserve-root, o utilitário lê o nome como opção: escreva rm -- "$arquivo", cp -- "$origem" "$destino", chown -- "$dono" "$alvo". Vale também para grep -- "$padrao" — um padrão que comece com hífen vira opção do grep, e se ele vem de entrada do usuário isso é uma forma de alterar o comportamento do comando à distância. Para glob em diretório arbitrário, a defesa complementar é for f in ./*: cada item passa a começar com ./, nunca com hífen. E valide antes de qualquer efeito colateral — quantidade mínima de operandos, coerência entre opções (-n com -o é incompatível) e se o destino é gravável.
⚡ Resumo rápido
  • Cadeia de if comparando $1 falha em silêncio na ordem trocada, na flag agrupada, na opção depois do operando e no argumento faltando.
  • getopts traz a convenção POSIX de graça: agrupamento -vn, argumento colado -osaida, OPTARG e parada no --.
  • Comece a cadeia com : (':vno:h') para ficar com o controle das mensagens — sem isso o Bash imprime as dele, em inglês, sem o nome do seu script, e os ramos : e \? ficam indistinguíveis.
  • shift $(( OPTIND - 1 )) não é opcional. Sem ele as opções continuam em "$@" e viram operandos, sem aviso.
  • getopts não faz opções longas — para --verbose e --saida=X, o laço while com case, que também trata o -- e rejeita opção desconhecida no ramo -*.
  • Dentro de função, local OPTIND; para analisar um segundo vetor na mesma execução, OPTIND=1. É variável global do shell.
  • --help sai na saída padrão com código 0; erro de uso sai em stderr com código 2. Trocar os dois faz a ajuda poluir pipeline e o erro passar despercebido na automação.
  • $0 é o caminho como foi chamado — pode ser relativo, pode ser link, e não serve sob source. Use ${0##*/} para mensagens e ${BASH_SOURCE[0]} para achar o diretório real.
🐉 No Kali
A validação de escopo entra logo depois da análise, antes de qualquer pacote sair da máquina. Verifique cada operando contra a faixa autorizada assim que o shift final entrega os alvos, e saia com código próprio se algum não pertence ao escopo — deixar a checagem para dentro do laço de varredura significa que os primeiros alvos já foram tocados quando o problema aparece. Varredura fora do escopo contratado é crime pela Lei 12.737/2012, e a análise de argumentos é o último ponto onde impedi-la ainda é barato. -o sem argumento é a falha que mais aparece em wrapper de ferramenta: coletar -o no fim da linha deixa OPTARG vazio e o arquivo de saída vira o diretório atual — ou pior, o próximo argumento, que seria o alvo. Com o : inicial, esse caso cai no ramo : e o script para com mensagem clara em vez de sobrescrever algo. Não repasse "$@" cru para nmap, hydra ou sqlmap: se o script encaminha opções que ele mesmo não entende, o usuário ganha toda a superfície da ferramenta por baixo do seu wrapper — inclusive o --script do nmap, que executa código NSE. Aceite uma lista explícita de opções e monte a linha da ferramenta com um array. Nome de saída de ferramenta ofensiva merece o --: relatório de gobuster e nikto carrega URL no nome, e URL tem hífen com frequência. E getopts dentro de função exige local OPTIND — sem ele a segunda análise continua de onde a primeira parou, e o resultado é uma opção ignorada, sem erro, com um alvo processado na configuração errada.
